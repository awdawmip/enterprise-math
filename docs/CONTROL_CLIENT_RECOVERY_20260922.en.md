### 1.1 Repeated dispatch with a capability mismatch is not renewed research

If this run's matching canonical `RESEARCH` receipt returns the same task again, and that task's latest accepted durable `CONTINUATION` explicitly satisfies all of the following:

1. Substantive mathematics/literature/proof units are marked `VERIFIED_COMPLETE` with supporting evidence;
2. The sole `UNFINISHED` unit is current canonical execution-record/Result freeze, a fixed native experiment, full latest-main repository validation, or another action explicitly dependent on a particular execution host;
3. The most recent execution left an exact durable frontier and explicitly recorded that the current class of ChatGPT execution host lacks that capability;
4. No verifiable change in task state, durable frontier, host capability, or relevant authorization has occurred since that handoff;

then the client must not create another CLAIM, publish another equivalent `CONTINUATION`, rerun completed research, or misreport `NO_DISPATCH` merely to demonstrate again that this host still cannot perform the action. The accurate classification is `CAPABILITY_MISMATCH_HEAD_OF_LINE`: preserve the task as the current canonical target, its unowned state, and existing frontier; record the missing capability and wait for a lawful executor that actually has it. This is not a new canonical dispatch state and changes no task priority, claimability, mathematical state, or Result state.

This rule suppresses only **claim-to-release loops without new information on hosts with the same capabilities**. It does not authorize a client to skip the canonical selector manually. If a matching executor later becomes available, it claims normally from the current real receipt and highest durable frontier. A new mathematical unfinished unit, frontier change, or capability change for the same task also requires the ordinary canonical flow again.

Availability of the private GitHub server's native writer is a real change in control-execution capability. ER/Result operations can no longer be permanently classified as this mismatch merely because ChatGPT lacks a local checkout. Scientific experiments, full-repository validators, or real permission errors the server cannot handle remain subject to their own current evidence.

If this head-of-line mismatch keeps blocking other research, only a Driver with current source-backed authority whose `AUTHORIZE` includes an applicable typed `research_task_delegation_scope` may use the existing canonical `assigned_research_task` entry to direct **another existing current task** to an independent Researcher/session. That entry's own publication, parent, assignment, CLAIM, and runtime gates still apply. Without this explicit authority, a Researcher, patrol agent, or ordinary client must not skip priorities, fabricate `BLOCKED`, change dependencies, or establish a second selector. It is then a real host-capability blocker that must be preserved truthfully.

The same applies to GOVERNANCE: if a canonical governance target needs only full-repository validation in a complete latest-main checkout and the current Driver host lacks that environment, record `LOCAL_VALIDATION_PENDING`. Do not manufacture progress through repeated CLAIM/HANDOFF, fabricated reviews, additional AUTHORIZE, or treating missing MCP as an authority failure. The Driver still checks independently actionable frozen Results, reviews/follow-ups, and other control work within existing authority.
