# Recovering a frozen return that has no current Result on main

`LEGACY_BRANCH_RESULT_INTAKE_REQUIRED` means the current publication remains
`FROZEN_RETURN / AWAITING_REVIEW`, but its operational immutable Result is absent
from canonical main. The native review writer cannot review that missing Result.
This is a control intake step; it neither reopens research nor requires contact
with the original researcher or Driver.

A Result belonging to another publication generation does not satisfy this
condition. A PR number, branch name, prose summary, or researcher self-verdict is
a lookup hint, not an immutable Result or mathematical acceptance.

An authorized replacement conversation performs this bounded procedure through
the connected GitHub transport:

1. Read the current task publication and continuation packet. Keep the frozen
   state and original mathematical scope. Do not issue a fresh research CLAIM
   merely because main lacks a Result.
2. Follow the packet's exact immutable candidates. If it gives only prose/PR
   hints, resolve the cited PR/head or execution branch to an actual commit and
   locate the existing Result with a bounded source lookup. Do not invent a
   Result path, ID, execution record, review disposition, or missing artifact.
   Respect the task's source firewall; control intake does not restore blindness.
3. Verify the original Result bytes, exact task/publication/ER/CLAIM bindings,
   taskbook pin, return, and every output-manifest blob and SHA-256. Include its
   actual execution record and all required dependencies. Preserve original
   authorship, contributor history, timestamps, source exposure and verdict.
   A generation mismatch requires explicit reconciliation under the ordinary
   current contracts; never relabel an old Result as the current generation.
4. In an isolated current Source copy, copy only the verified missing original
   bytes. Existing paths must already match exactly or be reported as conflicts.
   Run the original canonical Result/review audits and applicable reference and
   control checks. Do not weaken the original audit or bypass a scope block.
5. A genuine pre-cutover branch Result may be added to the exact legacy cutover
   pins only after verifying its historical immutable commit and authenticated
   handoff/publication evidence. Record those source facts. The cutover is not an
   audit exemption. Never fabricate a new `write_authorization` receipt or
   backdate an execution to make a legacy Result appear freshly authorized.
   Post-cutover records remain subject to the normal prospective write gate.
6. Publish the coherent original-byte intake and any justified cutover pin in
   one current-head CAS/non-force transaction. Reconcile a moved head without
   overwriting other work; verify every resulting remote blob and the canonical
   current-publication Result view. Only then route to a real, independently
   activated Driver for native review. Intake itself accepts no mathematics,
   grants no Working Truth/Foundation/promotion, and closes no parent objective.

If no genuine immutable Result exists, retain the frozen state and expose the
verified raw return and exact missing object. The current authorized Driver or
control maintainer must select an applicable ordinary compatibility/recovery
transaction. Do not synthesize an old Result or silently start new research.
