# 双语同步规则

## 一、规范语言模型

进取数论同时维护两套并行文字版本：

- 纯中文；
- 纯英文。

任何一套都不是附属翻译，也不存在唯一主语言。语义一致的一对文档共同构成规范内容。

如果两种语言在实质内容上发生冲突，仓库状态应视为不一致，必须先完成对齐。

## 二、文件配对

所有正式文字文档都必须登记在 `bilingual_pairs.json` 中。

一般命名方式：

- 英文：`NAME.en.md`；
- 中文：`NAME.zh-CN.md`。

根目录说明文件是明确例外：

- 英文：`README.md`；
- 中文：`README.zh-CN.md`。

## 三、同次变更要求

只要一个已登记文档对中的任何一边被新增、删除或发生实质修改，另一边必须在同一次推送变更中同步更新。

只修改一种语言的正式文档变更属于未完成状态。

代码、机器可读数据、数学证明文件、工作流配置以及不含面向读者的大段说明文字的语言中立元数据，不要求重复生成中英文副本。

## 四、纯语言规则

英文文字文档只写英文说明文字，中文文字文档只写中文说明文字。

以下内容可以例外：

- 数学符号；
- 代码与标识符；
- 文件路径；
- 网址；
- 为了精确引用而必须保留的文献姓名与标题；
- 不适合翻译的软件或项目专有名称。

规范文字文档中不得把中英文解释段落混写在同一个文件里。

## 五、语义一致

两种版本必须保持相同的：

- 结论状态；
- 定义；
- 公式；
- 示例；
- 限定条件；
- 证明状态；
- 研究问题；
- 参考资料；
- 路线决策。

表达方式可以根据语言习惯调整，不要求逐字翻译，但任何一边都不能单独增加或删除实质性的科学主张。

## 六、自动检查

`tools/check_bilingual_pairs.py` 负责验证：

1. 所有登记文档对都存在；
2. 英文文字文档中不存在中文字符；
3. 当前变更范围内，只要文档对的一边发生变化，另一边也必须发生变化。

GitHub 工作流 `.github/workflows/bilingual-sync.yml` 会在推送与合并请求中执行这个检查。

## 七、审查规则

正式文档变更在两种语言都完成语义一致性审查之前，不应合并。

后续发现错误时必须两边一起修，不能明知另一种语言已经过期仍只修其中一边。
