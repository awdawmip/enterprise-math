# 双语同步规则

## 一、规范语言模型

进取数论对已登记的规范文字维护两套并行版本：

- 纯中文；
- 纯英文。

任何一套都不是附属翻译，也不存在唯一主语言。语义一致的一对文档共同构成规范内容。

如果两种语言在实质内容上发生冲突，仓库状态应视为不一致，必须先完成对齐。

## 二、文件配对

作为共同双语规范内容采纳的文档必须登记在 `bilingual_pairs.json` 中。
研究笔记、草稿和任务内交接可以使用一种语言，不必为了保存或接续而另造翻译副本。
已登记的文档对继续适用本规则。
`docs/NAME.en.md` 和 `docs/NAME.zh-CN.md` 的命名表示已登记文档对；
未配对的研究材料使用普通笔记路径。

一般命名方式：

- 英文：`NAME.en.md`；
- 中文：`NAME.zh-CN.md`。

根目录说明文件是明确例外：

- 英文：`README.md`；
- 中文：`README.zh-CN.md`。

## 三、同次变更要求

已登记文档对发生新增、删除或实质修改时，应在将该改动采纳为共同规范版本前补齐另一边。
翻译可以随一个完整的整合批次完成；保存临时单语草稿或作者分支上的检查点不以翻译为前提。

尚待翻译的双语规范更新仍未完成，但不阻断独立研究或科学文件的保全。

代码、机器可读数据、数学证明文件、工作流配置和语言中立元数据不要求生成翻译副本。
其中的说明文字只有明确作为已登记的规范语言对维护时，才适用本规则。

## 四、纯语言规则

英文文字文档只写英文说明文字，中文文字文档只写中文说明文字。

以下内容可以例外：

- 数学符号；
- 代码与标识符；
- 文件路径；
- 网址；
- 为了精确引用而必须保留的文献姓名与标题；
- 不适合翻译的软件或项目专有名称。

规范文字文档中不得把中英文解释段落混写在同一个文件里。

## 五、语义一致

两种版本必须保持相同的：

- 结论状态；
- 定义；
- 公式；
- 示例；
- 限定条件；
- 证明状态；
- 研究问题；
- 参考资料；
- 路线决策。

表达方式可以根据语言习惯调整，不要求逐字翻译，但任何一边都不能单独增加或删除实质性的科学主张。

## 六、自动检查

`tools/check_bilingual_pairs.py` 核验文档对是否存在、英文文件的字符规则及标题层级是否对应。
提供 `--base <commit>` 时，还会检查所比较的变更范围是否同时修改了两边。
这些结构检查不能证明语义一致。

窄范围修改可用 `--paths <已登记路径> [...]` 检查指定文档对及其对应文件。
显式请求但未登记的路径会报错，不会被静默略过。不提供 `--paths` 时，仍检查完整登记表及文档登记情况。
要求同次变更检查时，应使用有效的比较基准。

GitHub 工作流 `.github/workflows/bilingual-sync.yml` 仅按需手动触发（`workflow_dispatch`）。
日常研究及科学检查点保存不以该工作流或完整登记表检查为前提。

## 七、审查规则

已登记的规范更新整合前应核对两种语言的语义一致性，维护者可以补齐翻译。
这不构成额外的数学接纳审查，也不要求翻译普通研究笔记。后续规范更正仍须对齐两边；
中间阶段的单语工作不能冒称已经完成双语同步。
