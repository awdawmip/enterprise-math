# Nollm 接入研究中控台的建议

日期：2026-11-20（UTC+08:00）。状态：架构建议与已核接口事实；尚未实施或部署记忆 MCP 工具。

## 推荐

复用已经能被研究对话调用的 Enterprise Math MCP Gateway，把 Nollm 作为现有 Python 后端里的独立记忆模块接入。首次接入无需另建一个让用户安装的新插件。

插件决定模型看见哪些工具，后端部署决定代码与状态在哪里运行。两者可以分别演进：以后需要独立运行资源时，可拆出 Nollm 后端而继续使用原插件入口。

## 代码与状态的安排

| 部分 | 组织方式 |
|---|---|
| Nollm 通用核心 | 继续在 Nollm 仓库维护，保留本地 CLI 和其他 Host 的调用能力 |
| EM 语义适配 | 公式、定理、条件、出处和适用范围的解释留在 Host／适配器 |
| Python 服务接入 | 增加薄模块，调用同一核心能力，不复制算法或重建记忆引擎 |
| 现有 MCP 网关 | 增加工具声明和对应转发，继续复用已有连接 |
| 原生记忆场 | 存在服务的独立持久目录，与代码发布目录分开 |
| 科学原文与正式研究状态 | 分别沿原 GitHub 来源和原正式控制接口处理 |

Sites 继续承担已有网关职责。Python 运行时与文件记忆场放在已有后端，不把完整 Nollm 运行时搬进网页或转发层。

## 对话应获得哪些能力

可以将已经存在的 CLI 功能映射为以下拟议工具。名称可按现有风格调整，当前尚未部署这些工具。

| 拟议名称 | 复用能力 |
|---|---|
| `em_memory_walk` | 观察 Surface、逐步选择、从一个最终物理入口召回 |
| `em_memory_show` | 读取指定判断及版本、条件、来源 |
| `em_memory_source` | 展开保存的精确原文引用 |
| `em_memory_save` | 保存 Host 已形成的有来源判断，或修订已有判断 |
| `em_memory_find` | 辅助字面查找，与原生导航分别表达 |

语义理解、条件比较、位置选择由当前大模型完成，服务执行存取和原生导航。首次接入不需要另部署推理模型或训练小模型。回源可适配现有精确来源读取能力，避免为同一份科学原文再维护第二套资料库；本地 Git 的 CLI 使用继续保留。

## 让科研保持直接可用

普通记忆查询和工作理解保存不应经过任务派发、CLAIM、RUN、Result 或正式审查的启动流程。记忆保存成功就确认该理解已持久保存；科学原件保存、Activity 关联和正式接纳分别依据真实状态处理，记忆操作本身不自动晋升结论。

记忆调用也不应排到全局正式控制写队列后面。该场按既有单写者方式，由服务中的一个实际访问点串行操作；如果部署有多个 worker，应由同一实际持有者处理该场，而不是每个 worker 各自持有一份进程内状态。无需为本实验增加分布式锁或新调度平台。

使用现有持久化和 `--field` 对应的明确目录，重启后重新打开已有工作场，代码升级继续使用已续写内容。用现有项目资产保存方式保留有价值的记忆阶段成果，不把每次查询都变成 Git／Activity 手续。

继续遵守用户的内部试验要求：简单直接实现，不新增防御性代码、重复验证、哈希链、鉴权框架或自证平台；复用当前连接已有的访问处理。接口参数与普通类型服务于实际调用，不另造通用命令执行入口。当前先用于 TASK／知情研究；FREE A 使用其适用来源视图。

## 部署验收

在真实研究对话中看到并成功调用新增工具，然后完成：观察记忆、选择入口、取回判断与原文、保存一项有来源的理解或更正、由不带前次工作上下文的后续会话取回。已有场在一次服务重启后仍可打开。

原有中控台状态及必要资料读取继续可用，记忆调用无需领取正式任务。部署是否完成以对话实际调用与持久结果为准，后端函数存在、站点发布成功或工具名称出现都不是单独的完成证据。现有任务可能保留旧工具发现状态，应核验实际使用会话；不为接入先批量修改研究调度。

本次接入解决当前研究对话的直接调用与持久使用。此前试用尚未证明端到端算力净节省；应继续根据实际跨线复用、重复阅读减少和记忆维护成本判断效果，不能把工具接通当成科研效率已经改善。

## 何时考虑独立插件

当 Nollm 已实用于多个项目，并需要单独的通用记忆入口、发布节奏或使用范围时，独立插件才有明确价值。若只是后端资源互相影响，可以先分离运行进程，保留同一个插件转发；新插件本身不提供计算或存储隔离。

本轮建议因此是：先复用现有插件和服务入口，保持 Nollm 模块与状态独立，通过实际研究使用来决定后续拆分。
