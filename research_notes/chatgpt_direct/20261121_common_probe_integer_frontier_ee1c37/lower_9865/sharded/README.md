# 原整数覆盖的可恢复前缀分批及一个完整 9865 分型

本目录只改变既有搜索的调度单位。`front_sharded.cpp` 保留 B/C 原引擎的合法类、仿射处理、剪枝、递归、候选顺序和解表恢复代码，将既有最外层前缀列表按连续区间执行。没有加入矩筛或其他新必要条件。

本归档同时固定一个费用 9865 的完整分型排除：

```text
9-557-2_10-744-1_10-747-5_11-936-1_12-1104-1_12-1116-2
```

它的全部 **5528 个原前缀、173 个批次**均已执行完毕，无解；覆盖节点 **60,478,750**，几何节点 5528，叶节点 3711。`receipts/` 保存每批真实终局，`expected_receipt.json` 保存整分型汇总。这不是整个费用 9865 层的完成声明。

## 保解与完整覆盖

原引擎对一个完整大小／费用分型恰使用下列三种入口之一：

1. 有预先规范化的 1116 类锚时，遍历相应输入文件中的 `Frame` 列表；每一项含剩余历史 `f` 和原来已经限制好的后续 1116 候选 `rows`。
2. 无此类锚、但含核心时，遍历相应核心数与完整十三点数的规范余集列表 `spaces[k,h]`。
3. 两者都没有时，按原规则选全库最稀少类型，遍历它的原仿射代表列表。

派生程序对同一有序列表只执行索引位于 `[begin,end)` 的项目。传给 `add_big` 的每个参数、已经消耗的各类型计数、候选列表及排序限制均与原程序相同。完整项返回无解后计数回溯到原值，这一点和原程序接着处理下一项所依赖的性质完全相同。

因此，将 `[0,total_frames)` 分为首尾相接、不重叠的区间，并完整排除每一区间，就等价于原程序完整排除同一分型。分批不要求不同前缀之间属于不同仿射轨道；原前缀列表的全覆盖及其允许的冗余已经由 B 的输入生成证明保证。

`make.py` 从固定源生成派生文件，`generation.json` 记录全部文本替换及 SHA-256。替换仅有输入读取区间、这三段最外层分派和输出总前缀数。核心递归及所有筛查函数没有修改。

## 完成单位与恢复

`run.py` 先向原生程序请求空区间 `[0,0)`，仅得到完整前缀数。这次零节点请求不构成任何前缀的无解证明。随后保存精确分批计划；默认每批 32 个原前缀。

每一批必须收到原生程序完整终局后才写临时 JSON，再原子改名为完成回执。恢复时只读这种完成回执，检查其原分型、范围、银行与源码摘要，不把 `running_*.json`、临时文件或未结束范围计为排除。任何计划参数改变都会拒绝沿用旧完成回执。

`coverage.json` 中 `complete` 只有在全部计划区间都有终局且确切覆盖整个索引区间时才为真。未完成时保留全部缺失批次。单个批次若找到整数解，程序保存原解表并停止，不能导出无解证书。

## 已执行的验证

| 原先已完成的对照分型 | 前缀数／批次数 | 几何节点 | 叶节点 | 覆盖节点 |
|---|---:|---:|---:|---:|
| `10-744-3_10-747-5_10-752-1_11-936-1_12-1104-2` | 6／6 | 6 | 2 | 23,136 |
| `9-557-4_9-591-1_10-744-2_12-1104-2_12-1116-3` | 504／16 | 30,103 | 375 | 521 |

两项的分批总计均逐字段等于 C 中原单次搜索终局。第二项还保留了前缀内尚未消费的 1116 类，因此检查了原后续候选列表和排序门槛的实际传递。

另对第一项先只执行前三批，确认覆盖审计明确报告缺少批次 3、4、5，随后再完成后三批；恢复后的完整终局仍与原始 23,136 个节点一致。回执是 `control_comparison.json`、`control_punct_comparison.json`、`resume_validation.json`。这些对照辅助核对实现，完整性论证来自上述逐项相同的分派关系。

当前应用限于原银行已经完整支持的费用 9861—9870 输入。无核心且没有 1116 锚的第三种入口在这一区间的分型中不会出现；其循环替换仍保持相同逐项关系。

## 来源与使用

`input_bindings.json` 固定原 B/C 银行、核心与锚点文件、两份原头文件、派生源码和实际编译产物。已经实际核对工作目录的全部原输入逐字节等于这些绑定。完整银行仍为 426,500 个合法类、27 个类型；原菜单、费用和银行全覆盖论证未改变。

归档的统一复验入口会从相邻 B/C 源码逐字重建派生源，核对两份原头文件、全部 173 批、区间无遗漏以及三项实现对照：

```text
python replay.py --lower <固定B/C的lower目录> --mode audit --output sharded_verification.json
```

可增加 `--work <既有完整原输入目录>`，实际重查 18 个输入文件摘要。附带的 `verification.json` 已使用这个选项执行；它没有声称再次运行 60,478,750 个节点。

附带审计还用 `--binary <实际执行的保留程序>` 核对了原二进制 SHA-256：

`295b925a821d15fd55128d74eac3872bd06912bc348791fe626793e867488665`。

全量入口在临时目录从已经逐字重建并验证的派生源码重新编译，使用已经核对的原头文件，随后执行这个明确路径的产物。回执记录源码、头文件、编译命令、编译器版本和实际执行产物的摘要，并在搜索前后确认产物没有改变。不同编译环境的二进制摘要不必与原保存产物相同；其来源及精确计算结果仍须核对。

在全新临时目录从原菜单重新枚举种子、生成银行及锚，编译派生源并实际重跑全部 173 批：

```text
python replay.py --lower <固定B/C的lower目录> --previous <完整前驱归档> --mode full --output sharded_full_verification.json
```

`make.py` 保留实际研究时使用的源生成版本，默认路径对应原工作布局；可移植归档应使用上述 `replay.py`，不要求还原原工作目录名称。

以下低层命令供已编译原生程序的研究工作目录使用。执行或从已完成批次恢复一个分型：

```text
python run.py --work <已核对的完整原输入目录> --tag <完整大小费用分型> --batch-size 32 --output <独立回执目录>
```

`--begin`、`--end` 可把**批次编号**分配给互不交的工作线程；计划本身仍覆盖全部前缀，局部线程结束不会被当作整分型完成。

仅在整分型完成后导出可供全层谱审计使用的终局：

```text
python export.py --work <原输入目录> --directory <回执目录> --output <分型终局.jsonl>
```

`export.py` 还会逐项校验全部原输入摘要，拒绝导出任何缺批次的分型。

`run_layer.py` 对同层其余分型使用**未改动的原引擎**，通过显式 `--exclude-tag` 将分批任务保留给独立线程；这些保留项会列在状态中，绝不提前算作完成。这避免两个驱动同时重复处理同一重型分型。

本目录在费用 9864 的冻结证书之外。派生搜索只有在某个完整费用层实际采用并满足全部完成条件后，才进入该层的新证书。未取得项目正式独立 Review。

根代理另行逐读了三种外层分派，并从固定原源应用 `generation.json` 的全部替换，得到逐字相等的派生源码；它也交叉检查了范围全覆盖与恢复逻辑。这个状态是**同团队实现交叉检查**，不等同于项目正式 Review。
